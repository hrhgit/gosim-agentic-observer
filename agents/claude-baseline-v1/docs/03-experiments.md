# 03 · 实验过程与结果记录

按时间顺序记录这一版基线从第一次跑通到定稿的每一步：发现了什么问题、怎么确认的、改了什么、
成绩怎么变。日期均为 2026-10-04（本机时区 UTC−7）。

## 0. 评测方式

- **评测数据**：主项目的 `evaluation_assets/formal-v4-self-generated-v2/`。正式卡 A–D 的公开输入
  原样不动，天气、事件、公告、预报、限时请求用引擎自带的生成器**自行生成**（固定种子）。
  v2 每张卡 6 条请求、3 个仪器故障，D 卡启用 Hard mode（数据丢失 + 隐藏指向偏差）。
  早期实验用的是 v1（请求和故障更少，天气与其余事件和 v2 相同）；v2 是开发中途主项目新生成的
  对齐版本，之后全部改用 v2，v1 的成绩单独放在 `results/evalset-v1/`。
- **记录用的成绩**一律来自 `tools/run_eval.py`：它调用未改动的官方本地裁判
  `examples/_local/runner/run_local.py`，智能体作为独立进程走 JSON Lines 协议，
  时间预算和计分都是平台同一份代码。
- **开发时的快速比较**用 `tools/quick_sim.py`：同一个引擎、同一套计分，但把智能体当作进程内的
  Python 函数调用，不经过管道和计时器，可以只跑前 N 夜。下面凡是标"快速模拟"的数字都来自它，
  只用于方案之间的相对比较。
- **真实时间上限**：平台在第一条请求后 1800 秒强制结束（引擎自身耗时也算在内）。CPU 预算按机器
  速度系数折算，这个上限不折算。本机白天同时在跑别的训练任务，速度系数在 0.4–5 之间波动；
  系数大于 1 时，`run_eval.py` 默认用引擎的组织者配置项 `OBSERVER_WALL_CAP_SECONDS` 把上限按系数
  等比例放宽（不低于 1800），以还原平台上"上限 = 2 × 预算"的比例。每次运行实际使用的上限写在
  各自的 `summary.md` 里。
- **参照**：主项目自带的官方高分示例 `examples/python-pro`，以 `OBSERVER_MODEL_DISABLED=1`
  （纯规则，不调用大模型）在同一套卡、同一个裁判下运行。

## 4. 留出集检验

`tools/make_holdout_set.py` 用新种子和引擎参考配置的事件频率（每 123 夜 6 雨、10 云、5 霾、4 寒潮、
1 风暴、4 次火箭、2 次地震）另生成一套卡，所有参数都没有在它上面调过。第一次跑（v0.3）平均 32,507.2，
12 个故障都报对了，但有几个拖了 5–17 夜才发现，原因和修复：

| 现象 | 原因 | 处理 |
|---|---|---|
| 持续 5 夜的寒潮期间开始的故障，寒潮结束才发现 | 只要有全天公告就不做突降判断 | 只在全天事件开始/结束前后两小时不判断 |
| 地震恢复期（公告持续十几夜）里开始的故障被当成地震损失 | 地震期间所有跨夜变化都记到效率上 | 效率按恢复曲线走，其余记到天气上，由档位证据发现；地震后第一夜只校准曲线 |
| 地震发生在夜末，第二夜被当成故障 | 跨夜突降规则没有排除"其间发生了地震" | 排除 |
| 雨停后第一批曝光触发误报 | 跨过关闭边界的曝光只开了一部分 | 公告关闭前后同样不做突降判断 |
| 通量和档位一起掉也被怀疑成故障 | 没有利用"故障不改变档位" | 两者同降记为天空 |
| 天气极好的夜晚误报 | 视宁度很好时天气自身起伏翻倍 | 突降阈值随天气水平放宽 |
| 一条公告对应两个高度不同的重叠遮挡扇区，盒子模型多挡了一块 | 一个方向只学一个矩形 | 改成"方位 → 遮挡高度"轮廓 |
| 一次付费误报（−150） | 缺口只有 25% 左右也去举报 | 举报按缺口分档，轻微缺口只用免罚额度 |

修复后（v1.0，正式记录）留出集：A 23,719.6 / B 44,991.7 / C 29,442.2 / D 33,292.6，平均 32,861.5；
故障多数在几小时内报对（少数在第二夜），没有付费误报。v2 上故障多在 2 小时内报对。
D 卡第三个故障开始时全年目标已基本做完、望远镜空闲，到下一条请求到来才被发现。

### 6.1 调权重和"判断全对"各值多少分

这一小节的实验都在基线的临时副本上做（改动未并入基线），用快速模拟跑完整赛季；
单次模拟之间有 ±100–200 分的波动（C 卡基线在快速模拟里是 29,323，正式运行是 29,394）。

**隐藏状态全知。** 规划器不变，估计器换成当前时段的真值：天气水平、仪器效率、档位、关闭、
遮挡扇区；故障在发生的那一刻举报。不给未来的信息。

| 评测集 | A | B | C |
|---|---:|---:|---:|
| v2 | 26,532（+75） | 46,183（−4） | 29,485（+91 至 +162） |
| 留出集 | 24,134（+414） | 45,501（+509） | 29,711（+269） |

v2 上没有可测的差别；留出集（事件多得多）平均 +397，约 1.2%。这是"在线把故障、天气、档位、遮挡全部判对"的上限。

**按当前天气调权重**（v2，A / C，相对基线 26,457 / 29,323）。天空水平与最近 21 夜中位数之比记为 r：
未饱和增益折扣乘 r^1.5 为 −22 / −61；时间价格乘 r 为 −27 / −49；时间价格除以 r 为 +15 / +53。都在波动之内。
基线本来就按当前天空水平定曝光时长，需要 1,500 秒以上的目标的最佳曝光平均落在天气排名 57–70% 的时段。

**暗目标的失分是结构性的。** 按"质量为 1 时曝满所需秒数"分组（v2，A 卡）：

| 所需秒数 | 目标数 | 满分合计 | 实得比例 | 曝满比例 |
|---|---:|---:|---:|---:|
| < 600 | 11,655 | 7,417 | 94% | 87% |
| 600–1,500 | 12,174 | 14,931 | 89% | 63% |
| 1,500–3,000 | 4,608 | 7,260 | 62% | 19% |
| > 3,000 | 1,563 | 3,152 | 30% | 1% |

后两组占 A 卡目标分缺口的约七成（C 卡约八成）。它们平均每个视场只有 6 个，凑不满 16 根光纤，
而一次曝光的所有光纤共用一个时长，于是多数是跟着别人的曝光"搭车"拿到一部分。

**完美排程能到哪里**（`tools/upper_bound.py`，线性规划；都假设提前知道整季天气、故障即时修复、时间在天区间分配到最优）。
目标分，v2：

| 模型 | 视场内的规则 | A | C |
|---|---|---:|---:|
| loose | 多次曝光可累加，光纤不共用时长 | 31,824 | 32,708 |
| shared | 真实规则（共用时长、只算最好一次），视场内任意 16 个目标可同时观测 | 29,100 | 29,659 |
| 基线 v1.0 实际 | — | 25,609 | 28,495 |
| shared_cells | 真实规则，光纤网格固定不动 | 23,438 | 24,819 |
| cells | 可累加，光纤网格固定不动 | 26,251 | 27,432 |

- loose 缺少"共用时长"这条约束，太宽，不能用来估计可达到的分数。
- 真实的最优在基线和 shared 之间：A 最多 +13.6%，C 最多 +4.1%。shared 假设每次曝光都能把光纤填满，
  这做不到，所以实际空间更小，小多少这个工具给不出。
- 基线比"固定网格下的完美排程"（shared_cells）高 9–15%，这部分来自平移视场去凑目标。
- shared 的方案里，按所需秒数 <600 / 600–1,500 / 1,500–3,000 / >3,000 的实得比例是
  A：98% / 97% / 82% / 44%，C：98% / 97% / 87% / 50%（基线 A：94% / 89% / 62% / 30%，C：97% / 96% / 78% / 43%）；
  它把 46–47% 的望远镜时间用在 1,500 质量秒以上的长曝光上（基线 26–32%），固定网格的方案只有 15–24%。
  也就是说，长曝光值不值，取决于能不能把光纤填满。
