# llm-observer-v1：读交接记录的巡天智能体

在 `../baseline-typescript-v1`（规则规划器 + 观测条件模型 + 仪器故障模型）之上加入大模型。大模型只做一件规则做不了的事：
**读新卡里 `observation_request.reason` 中的值班交接记录**，把它变成规划器能用的事实。指向、光纤分配、曝光时长仍由规划器精确计算。

## 大模型读什么、改变什么

新卡 A1–D1 每张有 45–90 条交接记录（每条约 800–1,000 字）：几个人逐行写，互相更正，夹着暗号、凯撒密码、摩斯码、唱名数字、
日文和无关闲聊。公告里没有的信息都在这里。

| 记录里的内容 | 提取成 | 智能体怎么用 | 与平台正式运行核对 |
| --- | --- | --- | --- |
| “3:15 前后动导星相机，此后整机效率会降，不是天的问题”“3:10 起吞吐量掉到 5 成，不是天的事，提单” | 故障线索（时刻、几成、是否要求申报） | 明确要求申报的立即 `report`；预告或说不清的，等自己的读数显示下降再报 | A1/B1/C1 的 18 个故障全部对得上，D1 6 个里 3 个有正确申报佐证 |
| “楼晃了，会一晚比一晚好，不用管” | 地震，不申报 | 恢复期内不让自己的检测器重复申报 | — |
| “西南的山实测 37 度，39 度以上没问题”“天顶距 52° 以内可以拍” | 各方向山脊高度 | 该高度以上不再按“可能被挡”打折，不必靠零分曝光去试 | 样本少，只在两个方向上看得清（山脊以下 91–100% 零分） |
| “北到东一带，门禁卡又要刷不开了”（暗号＝那个方向风大要关） | 关闭的扇区和时段 | 公告里对应方向的 `cold_snap` 条目按关闭处理：公告方向 ±30° 不分高度全关；再往外，记录点名的范围内按 85% 关闭，范围外到 45° 按 35% | 记录说关、公告也有条目时 98% 的光纤零分；记录说关而公告没有条目时 0% |
| “东到东南一带薄云，照拍”“云比较厚，效果打折” | 薄云/厚云时段 | 公告里的 `overcast`/`haze` 按实际轻重折算，而不是一律按重的算；“厚云拍不了”只按重度减光，不当关闭 | “厚云关闭”的时段里只有 1.5% 的光纤零分 |
| “周六晚上 23:30–03:30 圆顶电机检修，全停”“今晚停着，明晚也停着” | 公告里没有的停机时段 | 停机前不开长曝光；到点先用一次最短曝光确认确实全零，再一次等到结束 | 检修 95%、停电 100%、没说原因的停机 79–99% 零分 |
| “3/15 到 3/26 停电” 之类跨多夜的检修、停电 | 将要损失的夜晚 | 从“各天区剩余可见时间”里扣掉，停机前优先观测会错过窗口的天区 | 同上 |
| “今晚 18 点到 2 点要下雨，只能关顶”（暗号“暖气又坏了”） | 下雨时段 | **不据此关闭**：是否关顶只看公告 | 记录说下雨而公告当时没有 `rain` 的时段，93% 的光纤有分 |
| 紧急请求后面跟一句“那片天今晚风大关着，拍不到吧” | 关闭的扇区 | 这类请求的目标落在关闭扇区里，规划器自然不去追 | 平台上 6 个这样的请求无一完成，基线为它们拍了 62 次曝光全部零分 |

最后一列来自 `tools/check_notes_against_formal_runs.py`：把读记录得到的每个时段，和下载到的四张卡正式运行里每次曝光每根光纤的
得分逐一对照（零分＝确实拍不到）。上面的用法是按这份对照定的，而不是按记录的字面意思。

读记录的结果先过格式和范围检查，再进入事实表；日期换算、当地时间转 UTC、“那晚 0 点以后算次日”、方位角区间都由程序算，不交给大模型。
公告和曝光反馈仍是“现在正在发生什么”的依据：记录说明一条公告**是什么**（薄云还是关闭）、公告里**没有什么**（停机、山多高）、
以及**接下来会怎样**。几条防止读错造成损失的规则：

- 记录与反馈冲突时以反馈为准：在声称的山脊高度之上连续三次被挡，就撤回该高度；声称停机但确认曝光有分，当晚不再理会这条停机。
- 记录说某方向关闭，但当前公告里那个方向没有任何条目：不回避（何时何地以公告为准，记录只说明它是什么）。
- 故障申报分两种线索：
  - 记录里明确要求处理的（“提单”“叫工程组”“该打那个电话了”，或任何别的说法，由大模型判断）：立即申报，免罚次数用完后也照报。
    这类记录在能核对的三张卡上每一条都对应真实故障；而等自己的读数证实，在地震把读数盖住时曾经白等了两三天。
  - 预告（“3:15 前后动导星相机，此后效率会降”）或说不清的记录：到点后等自己的读数显示下降再报；预告过、到点 45 分钟
    仍没有可用读数、且两次免罚都在手时，用一次免罚申报去试。没有预告、只说“读数有点低”的不盲报。
- 同一个故障的第二条提醒不会重复申报：故障首尾相接、一次正确申报修好当时那一个，所以起点早于上次正确申报的线索一律作废。
  任何一次申报被判错，说明那一刻没有故障，此前所有“现在该提单”的线索一并作废。
- 自己的检测器（规则和故障模型）在记录接管申报之后只保留免罚的申报：按记录申报已经报对过、且免罚次数用完时，检测器想申报一律不发。
  原因：故障没人修的时候，检测器报警多半落在真故障上；每个故障都在一小时内按记录报掉之后，留给检测器的只剩天气、地震和停机，
  本地四张卡上，大模型版里检测器自己发起的 13 次申报只对了 1 次，而免罚之外每错一次扣 150 分。
- 判断“读数有没有掉”只用真正测到吞吐量的曝光：目标全部曝光饱和的长曝光量不出吞吐量，不算读数，
  否则会把“预告的故障到点后一直没有读数、用免罚申报去试”这一步挡住。
- 记录写明“是晃动造成的，会慢慢恢复，不必处理”时，地震后 7 天内智能体自己的检测器想申报会被压住（检测器分不清
  “地震后读数低”和“故障”，记录能分清）。记录另外点名的故障照常申报；自己的读数又出现一次新的突降时也照常申报。
- 读记录的代码若抛出异常，自动关闭这部分功能，其余按基线规则继续运行。

目前只提取、没有用于决策的内容：逐夜“偏好/偏差”的长期预报。

## 代码结构

```
src/agent.ts              协议主循环；提交记录、按真实时间余量等待、应用事实、故障申报、停机等待
src/handover/text.ts      确定性清理和解码：零宽字符、数字中间的颜文字、摩斯、凯撒、唱名
src/handover/prompt.ts    提取提示词和输出格式
src/handover/extract.ts   校验大模型输出并换算成事实（日期、时区、方位区间都在这里算）
src/handover/reader.ts    运行时调度：每条记录后台调用大模型，结果到达后并入事实表
src/facts/store.ts        事实表：时段、山脊、故障线索、来源、去重
src/llm/client.ts         OpenAI 兼容客户端：多服务顺序切换、思考模式、并发上限、本地缓存
src/sim/clock.ts          仅本地评测用（SIM_WALL=1 才启用）：按平台实测规律记真实时间的虚拟时钟
src/core/*                规划器与状态估计（来自基线；conditions.ts 增加了对事实的使用）
src/models/*, runtime/    两个已训练模型的调用（与基线相同，见 MODELS.md）
```

字符级的解码不交给大模型：245 条真实记录里的 238 行摩斯、51 行凯撒、73 处唱名全部由 `text.ts` 解出，以 `〔…解码: …〕` 附在原文后面再给大模型读。

## 模型服务配置

按下面的顺序使用，缺密钥的跳过；某个服务回答“无额度/未授权”后本次运行不再使用它，自动换下一个：

| 顺序 | 环境变量 | 说明 |
| --- | --- | --- |
| 1 | `OPENAI_API_KEY`、`OPENAI_BASE_URL`、`OPENAI_MODEL` | 平台“密钥与网络”里队伍自己的模型服务 |
| 2 | `KIMI_RELAY_API_KEY`（可选 `KIMI_RELAY_BASE_URL`、`KIMI_RELAY_MODEL`） | 主办方中转；每队同时最多 2 个请求，客户端已按此排队 |
| 3 | `KIMI_API_KEY`（可选 `KIMI_BASE_URL`、`KIMI_MODEL`） | Kimi Code 订阅，默认 `https://api.kimi.com/coding/v1` |
| 4 | `DEEPSEEK_API_KEY`（可选 `DEEPSEEK_BASE_URL`、`DEEPSEEK_MODEL`） | DeepSeek |

模型名默认 `kimi-for-coding`（K2.8）。`LLM_THINKING=off|low|default` 选择思考模式，默认 `off`
（`thinking: {"type":"disabled"}`）；`low` 发送 `reasoning_effort: "low"`。`LLM_PROVIDER_ORDER` 可改顺序。

没有任何密钥、或平台设置了 `OBSERVER_MODEL_DISABLED=1` 时不读记录，行为与基线相同。记录要么由大模型读，要么不读：
曾经有一个不调模型、只认关键词的读法，因为换个说法就认不出，已经去掉（RESULTS.md 2b）。
`HANDOVER=off` 完全不读记录，用于对照。

本地开发：在本目录放一个不进包的 `.env`，用 `LLM_ENV_FILE` 指向已有的密钥文件（只读取上表列出的变量名），
`LLM_CACHE_DIR` 把每次回答按“模型 + 提示词”存盘，重复本地评测不再消耗额度，结果也可复现。

## 真实时间预算

等大模型不消耗模拟时间，也不计入 CPU 预算，只消耗每张卡 30 分钟的真实时间上限。但真实时间正是这类卡上最紧的资源：
下载到的平台正式运行里，裁判每次决策的耗时从开局的约 0.02 秒涨到收尾时的 0.4–1.1 秒；原版跑完 A1 约用 590 秒、
C1 约 980 秒、B1 约 1,350 秒，D1 在巡天还剩近三个月时就用完了 1,800 秒。读一条记录约 8 秒，每张卡有 45–90 条。
在真实时间已经不够用的卡上，多等的每一秒都要用“曝光次数变少、单次变长”来换，得不偿失。
所以规则是**只用富余的真实时间去等**：

- 富余量 = 剩余真实时间的 80% − 按“不受限制时规划器自己选的曝光节奏”跑完全程所需的裁判耗时。
  用不受限制的节奏来算，是因为已经被压慢的节奏总会显得“还有时间”。
- 每收到一条记录，按“富余量 ÷ 预计还会收到的记录数”记一笔可等时间（每条最多 30 秒）；攒够一次读取的时间
  （约 1.3 倍的平均耗时）才等，否则不等、照常决策，结果到达后在后面的决策并入。
- 没有富余（真实时间已经在限制曝光次数）时一条都不等，读出的结果到达后才生效。

另有两处与大模型无关、为节省真实时间做的改动：巡天后期无事可做时一小时醒一次（原来每 15 分钟一次）；
零奖励的请求（交接记录就是以这种请求的形式送达的）不再参与天区估值。

这套等待规则只在真实时间吃紧时起作用，目前还没有在接近平台的计时条件下验证过；现阶段的本地对比先不计真实时间压力
（见“本地评测”），它在那里不起作用。

## 构建、运行、打包

```sh
npm ci --include=dev && npm run build     # Node.js 22
npm run test:notes                          # 读记录部分的单元测试（不需要模型）
npm start                                   # 协议入口
npm run pack                                # artifacts/llm-observer-v1.zip
```

两个已训练模型的运行环境与基线相同：比赛 Linux 上由 `runtime/setup.cjs` 在构建阶段安装，本机设置 `BASE_MODEL_PYTHON`。

## 本地评测

```sh
npm run notes:extract -- --card <卡目录> --out results/extract-a-off.jsonl   # 只跑读记录，输出提取结果
python3 tools/compare_extractions.py results/extract-a-off.jsonl results/extract-a-low.jsonl   # 两次提取逐项对比
python3.12 tools/build_note_aligned_set.py                                   # 生成与交接记录一致的本地评测集

SET=formal-v5-new-four-note-aligned-v1
python3.12 tools/run_eval.py --tag <名字> --eval-set $SET --wall-cap 21600 --keep-bulky --env LLM_CACHE_LATENCY=0   # 大模型读记录
python3.12 tools/run_eval.py --tag <名字> --eval-set $SET --wall-cap 21600 --keep-bulky --env HANDOVER=off          # 完全不读记录
python3 tools/analyze_runs.py <名字1> <名字2>                                # 分项对比：故障申报延迟、全零曝光时间等
python3 tools/check_notes_against_formal_runs.py                             # 读出的每个时段与平台正式运行的得分对照
node tools/paraphrase_check.cjs                                              # 把“提单”之类的说法换掉，看大模型还认不认得出
```

现阶段的对比先不计真实时间压力：`--wall-cap 21600` 把真实时间上限放到裁判允许的最大值，谁都不会被压慢，
等大模型也没有代价，比的只是“读到的信息值多少分”。这种跑法下机器忙闲只影响跑多久，不影响结果。
每张卡的 `trace.log` 是智能体的完整日志（不含逐次决策的模型记录），用来查某次申报、某次等待是哪条规则触发的。

以后要算真实时间这笔账时有两个开关（都还没有和平台记录逐项核对过，结论要谨慎用）：

- `--sim-wall`：智能体内部用一只“虚拟时钟”记账——每次决策按平台正式运行里实测的规律记裁判耗时
  （随累计分配的光纤数 ×（1 + 已发请求数）线性增长，四张卡各自拟合），每读一条记录记 `--llm-latency` 秒（默认 8），
  记满 1800 秒就不再观测。结果不受本机忙闲影响。只对本目录的代码有效，对照组用
  `--env HANDOVER=off --env BASE_IDLE_WAIT=0 --env BASE_ZERO_REWARD_SKIP=0`（规划和节奏与基线相同）。
- `--platform-timing`：真实计时，上限取 1800 秒 × 本机速度系数，缓存的大模型回答按同一系数延迟返回。
  只有机器空闲、同时跑的卡很少时才有意义。

评测集说明见 `evaluation_assets/formal-v5-new-four-note-aligned-v1/README.md`：正式公开输入和已收到的公告、请求原样保留，
隐藏条件是自行推测并与交接记录对齐的，**不是官方隐藏数据**。结果记录在 [RESULTS.md](RESULTS.md)。
