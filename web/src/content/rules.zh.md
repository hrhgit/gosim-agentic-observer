## 1. 参赛资格与队伍

1. 面向全球个人与团队开放。每人一个账号。
2. 队伍 1–3 人。每人只能属于一个队伍。提交以队伍名义进行。
3. 主办方、评测平台维护者及其直接合作者不参与评奖；其队伍在榜单上标记为隐藏。
4. 队名与内容须遵守行为准则（第 8 节）。

### 练习赛规则

1. 下载示例项目，用其中的本地练习卡在本地运行智能体并查看得分；把智能体打包，在「参赛」页提交完整项目（公开 GitHub 仓库或 ZIP），即「练习赛榜」。平台在云端逐轮运行你的程序（和比赛相同的评测流程），每次评测在全部练习卡上各运行一次，每张卡运行时限 900 秒。
2. 每日评测次数以「参赛」页显示的额度为准，按 UTC 0 点（北京时间 8 点）重置；因平台原因失败的不计次数。调用模型只能使用本队自己的模型 API 密钥。
3. 练习榜按任务卡分别排名，每队保留每张卡的最高分；严格同分时先提交者在前。练习成绩不决定奖项。
4. 语言与算法不限，练习时不强制使用大模型。注意：评奖要求作品在自然语言理解、数据解析、任务规划、行动决策、工具调用、计划自适应等环节中，至少两个环节采用智能体（大模型驱动）技术（第 3 节第 6 条），建议现在就按这个要求准备。
5. Kimi Coding Plan：跑通练习赛（至少获得一次成功评分：完整项目评测已评分）的前一百支队伍，每队获得一个 Kimi Coding Plan 兑换码，先到先得，发完为止。组委会发放后由队长在控制台领取，全队成员都能在控制台查看。使用时接口填 `https://api.kimi.com/coding/v1`，模型填 `kimi-for-coding` 或 `k3`。隐藏队伍和测试队伍不参与发放。

## 3. 提交内容

1. 提交完整项目的公开 GitHub 仓库链接（默认分支，也可指定分支、标签、commit 或项目子目录）或不超过 50 MB 的私有 ZIP，项目语言不限。平台检查后，由你审阅并确认固定的源码版本、启动设置和提出的适配文件。
2. 正式比赛仅接受完整项目，不接受 CSV 文件或本地 CSV 会话。
3. 评测逐轮提供当前观测：服务器先记录本轮决策，再提供下一轮数据。未来天气、事件和仪器故障保密。
4. 所有队伍的每日评测额度相同。一次评测在任务卡 A、B、C、D 上各运行一次，每张卡运行时限 900 秒。每队每天的评测次数以「参赛」页显示的额度为准，按 UTC 0 点（北京时间 8 点）重置；额度内可自由评测；每队最多可同时进行 4 个评测（一组「评测 3 次取平均」算 1 个，组内 3 次依次进行）。因平台原因失败的评测不计入额度；项目自身构建失败、崩溃或输出不符合协议导致的失败照常计入。「参赛」页另提供「评测 3 次取平均」自检：同一版本连续评测 3 次，占用当天 3 次评测，评测记录中显示各卡及综合的平均分和 3 次之间的最低–最高分。这 3 次评测各自按普通评测计入线上榜，3 次的平均分不上榜。
5. **最终版本。** 比赛期间，队伍任一成员都可以在「参赛」页面把本队一个已确认（且未撤回）的版本标记为最终版本，并可在比赛结束（10 月 7 日 23:59，UTC+8）前随时更改或取消；比赛结束后锁定。若始终未选择，默认使用本队线上最高分评测的版本。已选为最终版本的版本不能撤回。
6. **智能体技术要求。** 作品需在自然语言理解、数据解析、任务规划、行动决策、工具调用、计划自适应等环节中，至少有两个环节采用智能体（大模型驱动）技术，才视为合格。组委会主要通过 Claude 对最终版本代码的分析来判定。平台不强制每一轮评测都调用模型（第 4 节），但不满足本条的作品不参与评奖。

## 4. 运行与模型 API

1. Python 是平台运行器，不限制项目语言。平台在指定容器中运行已确认的版本。
2. 模型调用可选，由选手自备 API 和额度，平台不提供模型额度。服务商、协议和模型均不限，可以同时使用多个。请在「参赛」页的「密钥与网络」中保存程序需要的变量（如 API 密钥、接口地址、模型名），评测时这些变量作为环境变量提供给程序。评测期间，程序可以通过 HTTPS（443 端口）和 HTTP（80 端口）访问公网上的任何地址；其他端口、内网地址、本机地址和云平台元数据地址均不可访问。平台会记录程序访问的每个地址（域名与端口、连接次数、收发字节数、首次和最后时间），不记录任何内容；记录附在本队的运行日志和结果文件中，主办方也可查看。密钥加密保存在服务器上，只在评测和核验时使用，页面上只显示末尾 4 个字符，可以随时更换或删除，并在隐藏决赛成绩公布（核实）后自动删除。评测时无需保持页面打开。不要将密钥放入项目源码。
3. 允许使用外部算力和外部服务，包括自备的模型 API 和自有服务器。平台容器（2 核 CPU、2 GB 内存）的限制只约束在平台上运行的部分。
4. 每一轮决策必须由程序自动做出，禁止人工参与或代为决策。程序可以访问外部服务，但不得借此让人工参与决策。
5. 试图读取其他队伍数据、篡改评分或故意耗尽平台资源，可以导致取消资格。

使用模型时，在「密钥与网络」中保存密钥等变量，例如 `OPENAI_API_KEY`、`OPENAI_BASE_URL`、`OPENAI_MODEL`。程序用常见 SDK 直接调用服务商，每次请求自行选择模型，也可以同时调用多个服务商（例如简单步骤使用较快、较省的模型，关键步骤使用更强的模型）。平台会设置 `HTTPS_PROXY`，常见 SDK 无需额外配置。模型调用的费用由本队承担。

## 5. 评分

每张任务卡的得分由公开的评分器按该卡 `config/v4_score_config.json` 中的参数计算，参数在 `initialize` 消息中完整下发。以下为当前各卡的取值；完整协议与公式见下文和[任务卡](/cards)页面。

1. **巡天与动作。** 每张卡是一季巡天，太阳低于 −18° 时可以观测。智能体每次决策发送一个动作：`observe`（指向天空，给光纤各分配一个目标，曝光 60–3600 秒，声明观测程序 DARK、BRIGHT 或 BACKUP）、`wait`、`report`（报告仪器此刻有故障）或 `finish`。光纤数量和排布按各卡配置（`config/v4_fiber_config.json`，也在 `initialize` 中下发），请以运行时收到的数值为准；目前公开的练习卡 α–δ 均为 16 根（4×4）。
2. **目标得分。** 目标必须落在分配给它的那根光纤的方格内，并且整个曝光期间不低于 30° 高度角，才能得分。完成因子 = min(亮度 × 曝光秒数 × 天空质量 ÷ (f0 × T0), 1)，其中 f0 × T0 取自该卡计分参数（`flux_zero_point` × `exposure_zero_point_seconds`，多数卡为 0.5 × 900 = 450），目标得分 = 科学权重 × 完成因子 × 程序加成。
3. **程序加成。** 声明的程序与该目标所处的天空档位一致时，得分乘以 DARK 1.20、BRIGHT 1.12、BACKUP 1.06；不一致时乘以 1.00。
4. **只算最好的一次。** 同一目标可以重复观测，但多次曝光不累加，只计最高的一次得分。
5. **必观测目标。** 每个未完成的必观测（required）目标扣 50 分；完成要求最高完成因子不低于 0.5，程序加成不能替代这一门槛。
6. **均匀覆盖。** 按 10° 赤经条带计算各条带的完成比例，用 Jain 指数 J 衡量均匀度，扣 200 × (1 − J) 分，最多扣 200 分。
7. **仪器故障报告。** 仪器故障不出现在简报和预报里，只能从曝光得分判断。`report` 时确有未修复故障：+100 分并立即修复；每次正确报告之后，误报在卡片配置的免罚次数内不扣分，之后每次 −150 分；连续 `report` 另有次数上限。
8. **限时观测请求（R_request）。** 巡天期间，卡片可能按时发布限时观测请求（`new_messages` 中的 `observation_request` 消息，决策快照的 `active_requests` 显示实时进度）。请求列出一组目标、最少完成数、完成门槛、奖励和截止时间；在请求发布到截止之间完整完成的有效曝光自动计入，无需另行接受。达到最少完成数（按完成因子判定，程序加成不计入）即在截止时获得该请求的奖励，未完成不扣分；截止时发送 `observation_request_result`，数据丢失使曝光作废时会重发更正（`revised: true`）。
9. **总分** = 各目标最好得分之和 − 50 × 未完成的必观测目标数 − 均匀度扣分 ± 故障报告得失 + R_request（已完成的观测请求奖励之和）。
10. **时间限制（计时规则）。** 每张卡有 900 秒的**标准化 CPU 时间**预算。只计智能体在自己回合内实际使用的 CPU 时间：回合指从平台发出每条 `decision_request` 到收到回复为止；CPU 时间由平台从智能体容器的系统记账读取，包含全部进程和线程。这段 CPU 时间除以本机速度系数后计入预算。速度系数由平台在同一台评测机器上用固定的校准程序测得（开始前测一次，运行中约每 60 秒复测，测量时暂停智能体），评测机器的中位速度为 1.0，机器越慢系数越大。等待（例如等待模型接口或网络）和平台模拟、处理的时间都不计入预算。每条请求的 `wallclock.remaining_seconds` 是剩余预算，同时提供 `speed_factor`、累计的 `cpu_seconds`、`wait_seconds` 和距实际时间上限的 `wall_remaining_seconds`；请以 `remaining_seconds` 为准安排计算量，自行测得的 CPU 时间除以 `speed_factor` 后与预算同一单位。为防止程序卡死并控制评测时长，每张卡另有 30 分钟的实际时间上限，到达上限时同样结束。预算或实际时间用完、智能体出错（`agent_error`）或主动 `finish` 时巡天结束，此前的观测照常计分，终局扣分照常适用。本条计时方式自 2026 年 10 月 4 日起适用于全部新评测（练习赛、线上比赛和隐藏任务卡评测）；此前已完成评测的成绩保持有效。
11. **黑客松任务卡 A–D。** 四张卡固定，对所有队伍相同，不按队伍随机生成。比赛开始时公开卡片页面和公开输入（目标、天区轮廓、站点、望远镜与光纤、观测日程、计分参数）；天气、预报、事件和仪器故障不公开，评测时智能体只逐步收到简报和预报。平台先记录本轮决策，再提供下一轮数据；不能预先提交未来轮次或替换已经接受的决策。本队每次评测的结果 ZIP 可以下载。
12. **评测成绩与线上榜。** 一次评测的成绩是 A、B、C、D 四张卡得分的算术平均；四张卡全部完成后才进入线上榜。线上榜取每队最高分的那次评测，不能拼接不同评测中各卡的最高分；榜单同时显示每张卡的得分。
13. **隐藏任务卡 E–H。** 比赛结束后，主办方在四张选手从未见过的隐藏任务卡 E、F、G、H 上，对每队的最终版本（第 3 节第 5 条）在每张卡上各评测 3 次，每张卡同样 900 秒，不占每日额度。每张卡的成绩取这 3 次评测的平均分；最终成绩是 E–H 四张卡平均分的算术平均；线上榜不决定最终排名。决赛中每张卡的 3 次评测同时进行，请确保你的模型服务能承受并发调用（同一队的 3 次评测共用本队的模型密钥和调用额度）。隐藏卡、逐步数据、运行日志和结果在主办方公布最终成绩前保密。多次评测取平均是为了减少程序自身运行波动对排名的影响。建议各队尽量让智能体在相同输入下表现稳定，例如让程序自身使用的随机数可复现（固定随机数生成器的初始值）、避免依赖运行速度或机器性能的策略，并可在比赛期间用「评测 3 次取平均」自检稳定性（第 3 节第 4 条）。

## 6. 排名、同分与核验

1. **最终排名**：只计各队最终版本在隐藏任务卡 E–H 上的成绩（第 5 节第 13 条），按得分降序排名。某次评测中某张隐藏卡因队伍自身原因未完成（如程序崩溃、超时、轨迹未通过核验）时，该次该卡记 0 分并计入该卡的平均；平台原因导致的失败不计 0 分，由主办方重新评测：为保证每张卡的 3 次评测同时进行，重新评测时该队的全部 3 次评测一起重新运行，原有结果作废（保留备查）。隐藏成绩严格同分的处理由主办方决定，并随成绩一起公布。
2. **线上榜**：比赛期间实时显示各队最高分评测（第 5 节第 12 条）；严格同分时先完成的评测在前。它只用于反馈，不决定奖项。主办方可在最后几小时封榜。
3. 隐藏卡决赛评测在线上赛冻结后由主办方统一运行，使用各队在「密钥与网络」中保存的变量，网络访问规则与线上赛相同，无需打开页面。程序会调用大模型的队伍，请在比赛结束（线上赛截止）前确认所需的密钥已保存。不调用模型的队伍不受影响。已保存的密钥在隐藏决赛成绩公布（核实）后自动删除。
4. 确认奖项前，主办方会对前列队伍做复现核验：可重新运行其最终版本，并可要求提供完整代码、所用外部服务与模型的版本和配置、评测期间的调用记录。核验结束前，请保持所用外部服务和已保存的密钥可用。无法运行、表现与上榜成绩明显不符或发现人工干预的，结果将被移除。
5. 若发现评分器缺陷，主办方可重新评分。评分器或参数的任何变更都会带版本号公告，并适用于该阶段全部提交。

5. 主办方关于资格、取消资格与奖项的决定为最终决定。
