# Agent Observer 官网对标分析与改进方案

> 对标对象：[GOAI 世界人工智能开源大赛](https://goaihz.com)  
> 分析日期：2026 年 8 月 22 日  
> 适用站点：`/survey26/`（巡天智能体 / Agent Observer）

## 一、结论摘要

Agent Observer 当前的核心优势是鲜明的天文主题、强视觉识别和清楚的赛题愿景；主要不足是赛事决策信息与参赛服务信息不够完整。页面更接近一张高质量的赛事海报，而 GOAI 已形成从认知、判断、报名到交付的完整赛事服务链路。

本轮改进不应复制 GOAI 的政企蓝色视觉或庞大的多赛道结构，而应学习它的信息组织与转化能力。在保留现有“观测站 / 夜空 / 900 秒决策”品牌表达的基础上，优先补齐首屏关键信息、评测标准、观测结果提交说明、FAQ、可信度信息和有效报名入口。

建议将官网目标明确为：

1. 让第一次访问的用户在 10 秒内判断赛事是什么、何时进行、奖金多少、是否适合自己。
2. 让有兴趣的用户在 3 分钟内理解如何参加、提交什么、怎样获胜。
3. 让准备参赛的用户可以在官网完成报名、组队、阅读规则、进入 CosmosBench 和查看排名。

## 二、对标范围与方法

本报告从五个维度比较 GOAI 与 Agent Observer：

- 信息架构：页面是否覆盖完整参赛旅程。
- 首屏表达：是否快速传达关键决策信息。
- 参赛转化：是否持续提供明确、有效的下一步行动。
- 赛事可信度：是否充分展示组织方、专家、合作伙伴和规则。
- 内容可执行性：参赛者能否据此完成开发、提交和现场准备。

GOAI 是综合性、多赛道、大规模赛事；Agent Observer 是聚焦单一科学任务的专项赛事。因此本报告关注可迁移的方法，不以内容数量或机构规模作为直接目标。

## 三、现状对比

| 维度 | GOAI | Agent Observer 当前状态 | 判断 |
|---|---|---|---|
| 首屏关键信息 | 集中呈现赛事规模、赛程、地点和报名入口 | 赛题愿景突出，奖金、形式和报名状态不够集中 | 应强化 |
| 赛事定位 | 明确说明面向人群、赛道和价值 | “每 900 秒决定下一次观测”辨识度很高 | 保留并前置 |
| 参赛路径 | 报名、手册、赛道详情、流程、FAQ 相互连接 | 已有报名、赛程和赛事说明，但入口关系较弱 | 应串联 |
| 提交要求 | 明确列出结果格式、截止时间与入口 | 尚未明确最终观测结果格式 | 高优先级补齐 |
| 评审与获胜条件 | 明确评审重点及阶段要求 | 仅概述科学产出、均匀性、效率和合规 | 应形成评分卡 |
| 奖项说明 | 奖金与资源支持均有独立展示 | 已新增 $5,500 奖金 Section | 已完成基础版 |
| FAQ | 覆盖资格、团队、现场、API、开源和奖金发放 | 暂无集中 FAQ | 高优先级补齐 |
| 信任背书 | 主办方、专家、社区、媒体和合作伙伴充分展示 | 主办与技术支持关系不够显著 | 逐步补齐 |
| 内容资源 | 参赛手册、模板、海报和公告可下载 | 赛事说明较完整，模板和下载物不足 | 应增加资源中心 |
| 转化入口 | 导航、内容区和页尾持续出现报名 CTA | 多处仍显示“即将开始”，缺少统一状态 | 上线报名前统一 |
| 品牌辨识度 | 稳健、机构化，但视觉相对通用 | 天文控制室与海报语言鲜明 | 不应削弱 |

## 四、值得学习的设计原则

### 4.1 首屏先回答参赛决策问题

首屏除了赛事名和一句话任务，还应立即显示：

- 总奖金池：$5,500。
- 线上培训：10 月 1–4 日。
- 线上比赛：10 月 5–7 日。
- 颁奖：10 月 17 日，GOSIM 深圳。
- 参赛范围：全球开放；个人及团队可参加。
- 主行动：立即报名。
- 次行动：查看赛题或赛事说明。

“每 900 秒做一次观测决策”应继续作为记忆点，但不能替代日期、奖金和报名状态。

### 4.2 按用户旅程组织页面

推荐首页顺序：

1. Hero：赛事定位、关键数字、报名。
2. Mission：一句话解释任务与输入输出。
3. Schedule：培训、决赛、颁奖。
4. Prizes：奖金结构。
5. Evaluation：如何评分、如何获胜。
6. Submission：如何提交智能体生成的观测结果。
7. Leaderboard：实时排名与评测入口。
8. Credibility：主办、技术支持、专家和合作伙伴。
9. FAQ：消除报名与参赛阻力。
10. Final CTA：报名、组队、下载手册。

长篇的科学背景、观测策略和技术细节继续放在赛事说明页，首页只保留摘要和深链接。

### 4.3 把规则写成可执行信息

参赛者需要的不只是“设计一个数字观测员”，还需要明确：

- 观测结果的文件格式、字段与大小限制。
- 每日结果提交次数、排行榜刷新方式和最终封榜规则。
- 平台如何校验并评分提交的观测结果。

未确认的规则应显示“待规则发布确认”，不可用推测性文案填补。

### 4.4 用可信度降低新赛事的参与顾虑

建议逐步展示：

- GOSIM Foundation 主办身份。
- CosmosBench 的技术支持与评测职责。
- 已确认的天文、巡天或智能体领域专家。
- GOSIM 深圳大会与会场链接。
- 官方联系邮箱、参赛社群和行为准则。
- 已确认合作机构；未确认机构不得提前展示。

### 4.5 保持单赛题网站的专注度

GOAI 的大量机构、赛道和资源内容服务于综合赛事规模。Agent Observer 不应照搬其信息密度。每个首页 Section 应只解决一个问题，详细内容进入赛事说明、规则、FAQ 或资源页。

## 五、分阶段改进方案

### P0：报名开放前必须完成

#### 1. 强化首屏信息层级

改动内容：

- 将 `$5,500`、`10.1–10.17`、`Online + Shenzhen Awards` 作为首屏指标展示。
- 将不可点击的“报名即将开始”替换为统一的状态组件。
- 报名开放后提供“立即报名”和“查看赛事说明”两个明确入口。
- 中英文名称固定为“巡天智能体 / Agent Observer”。

验收标准：

- 桌面端和移动端首屏无需滚动即可看到名称、日期、奖金和 CTA。
- 所有报名入口状态一致。
- 中英文页面核心数字完全一致。

#### 2. 新增评测标准 Section

建议字段：

- 科学产出。
- 天区覆盖均匀性。
- 时间利用效率。
- 天气风险管理。
- 规则合规。
- 决策可解释性。

验收标准：

- 首页提供人类可理解的评分摘要。
- 赛事说明页链接到正式评分公式或规则版本。
- 明确排行榜分数是否直接决定最终名次。

#### 3. 新增观测结果提交 Section

明确说明参赛者在本地构建并运行智能体，向比赛平台提交的内容只有智能体生成的观测结果，不提交智能体项目、源代码、架构说明或轨迹日志。

验收标准：

- 观测结果提交说明包含格式、截止时间和提交入口。
- 未确认项明确标为待确认。

#### 4. 新增 FAQ

首批问题：

- 不懂天文能否参加？
- 可以个人参赛吗？
- 团队人数上限是多少？
- 是否必须到深圳？
- 海外团队如何参加？
- 可以使用商业模型或 API 吗？
- CosmosBench 是否免费？
- 是否必须开源？
- 排行榜分数是否等于最终成绩？
- 奖金为税前还是税后，如何发放？

验收标准：

- FAQ 可以直接链接到具体问题。
- 答案来源于正式规则或团队确认记录。
- 待确认问题不做推测性回答。

### P1：赛事启动前完成

#### 5. 建立资源中心

内容包括：

- 赛事手册。
- Mission Card。
- Starter Kit 与基线 Agent。
- CosmosBench 使用说明。
- 观测结果模板。
- 常见错误与调试指南。
- 宣传海报和社交媒体素材。

#### 6. 增加组织与专家信息

只展示已确认信息，按“主办 / 技术支持 / 科学顾问 / 评委 / 社区合作”分类。人物卡片至少包含姓名、机构、角色和确认状态。

#### 7. 统一报名、组队与评测入口

建议形成单一流程：

```text
了解赛事 → 报名/登录 → 创建或加入团队 → 阅读规则 → 运行智能体 → 提交观测结果 → 查看排名
```

每一步应提供状态反馈和清晰的下一步按钮，避免官网、报名页和 CosmosBench 之间互相迷路。

### P2：比赛期间持续完善

#### 8. 赛事状态与公告

- 在导航或首屏显示当前阶段。
- 发布规则变更、系统维护、提交截止提醒和封榜公告。
- 所有公告带发布时间、版本号和影响范围。

#### 9. 排行榜上下文

- 显示更新时间、评测场景版本和封榜状态。
- 解释分数构成和同分规则。
- 提供 CosmosBench 完整榜单入口。
- 接口异常时显示明确状态，不应让空榜看起来像无人参赛。

#### 10. 结果与赛事沉淀

- 获奖团队、作品和现场展示。
- 可复现方案或技术文章。
- 赛事数据摘要。
- 下一届或社区持续参与入口。

## 六、实施优先级与工作量建议

| 优先级 | 工作项 | 预估复杂度 | 依赖 |
|---|---|---:|---|
| P0 | 首屏关键信息与 CTA | 小 | 报名状态与入口 |
| P0 | 评测标准 Section | 中 | 正式评分规则 |
| P0 | 观测结果提交 Section | 中 | 结果格式规范 |
| P0 | FAQ | 中 | 运营、技术、财务确认 |
| P1 | 资源中心 | 中 | 手册、模板、Starter Kit |
| P1 | 组织方、专家与合作伙伴 | 小—中 | 已确认名单与素材 |
| P1 | 报名到评测的流程串联 | 中—大 | Supabase、CosmosBench |
| P2 | 公告与状态系统 | 中 | 内容维护机制 |
| P2 | 排行榜解释与异常状态 | 中 | CosmosBench API |
| P2 | 结果归档 | 中 | 比赛结果与授权素材 |

## 七、待业务确认的数据

以下信息在团队版安排中尚未确定，网站不得自行补全：

- 现场邀请队伍数与总人数。
- 团队人数上限。
- 报名开放时间与截止时间。
- 是否要求获奖队伍必须到场。
- 差旅、住宿及现场接待政策。
- 奖金税务、币种、汇款与领取流程。
- 商业模型、外部 API、网络访问和算力限制。
- 开源范围及许可证要求。
- 观测结果格式、提交次数与封榜规则。
- 排行榜成绩和最终名次之间的关系。
- 已确认主办、技术支持、专家、评委及合作伙伴名单。

建议为这些字段建立一个运营确认表；确认后先更新单一数据源，再生成中英文页面，避免日期与规则再次分叉。

## 八、不建议照搬的内容

- 不复制 GOAI 的政企蓝色视觉体系；保留 Agent Observer 的夜空、观测站和控制室语言。
- 不复制综合赛事的超长首页和庞大 Logo 墙。
- 不用未经确认的专家、合作方和资源承诺填充可信度模块。
- 不把赛事规则只放在 PDF 中；关键规则必须可在网页浏览和搜索。
- 不设置多个含义不同的报名入口。

## 九、建议的下一步

1. 由赛事运营确认第七章中的 P0 数据。
2. 设计并实现首屏指标、评分标准、交付物和 FAQ 四个模块。
3. 将赛事名称、赛程、奖金和报名状态收敛到单一配置源。
4. 完成中英文内容审校、移动端检查和报名流程测试。
5. 报名开放后，以真实链接替换所有“即将开始”占位状态。

完成 P0 后，官网应从“赛事概念展示页”升级为“能够支持用户做出参赛决定并开始行动的赛事官网”。
